# cross-review

AI 的活总差一点，让它自己检查，又常常觉得自己没问题。`cross-review` 给技术方案、研究报告、文档和重要修改找另一家模型看一遍：三路独立审查，一路找问题，一路看哪里可以做减法，一路查外面的成熟做法。主 Agent 逐条裁决，再把该改的改好，让第二意见真正落到交付里。

## 什么时候值得多看一眼

- **方案准备定稿**：“定稿前 cross-review 这个技术方案。”对照最初想解决的问题，看有没有漏掉关键场景，哪些选择会影响后面的实现。
- **重要修改已经完成**：“用全新独立会话做一次实施后验收。”把最终改动和验证结果交出去，看做出来的东西有没有满足原始要求。
- **越做越复杂**：“给我一个跨厂商第二意见，尤其看看有没有不必要的复杂度。”专门找重复规则、过度防御和后续要一直养着的东西，看看哪些可以删。
- **想确认有没有更成熟的办法**：“这个方案帮我做三路审查，留意别人已经怎么解决。”查官方资料和成熟实现，把会改变当前选择的参考带回来。

## 核心流程

```text
原始需求 + 待审原文
        │
        ├─ Issues：正确性、遗漏、阻断项
        ├─ Simplification：冗余、过度防御、维护负担
        └─ Research：官方资料、成熟实现、行业实践
        │
        └─ 主 Agent 逐条裁决 → 实施 → 全新会话独立验收 → 最终交付
```

三路共享同一份原始材料，但角色合同不同，不要求每一路重复回答同一组通用问题。审查方只读，不修改工作区，也不替主 Agent 决策。

完整、可移植的运行合同见 [`SKILL.md`](SKILL.md)。公开仓是该合同的唯一维护源；具体机器上的 CLI 路径、权限和调用包装应放在本地适配层，不复制或改写核心协议。
